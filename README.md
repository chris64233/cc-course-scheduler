# cc-course-scheduler

课程排课服务。

保留现有业务代码与自动化测试，作为后续功能迭代的稳定起点。

## 开发环境

- JDK 21
- Maven Wrapper 3.9.9
- Spring Boot 4.1.1

迁移项目沿用现有 Spring Boot 版本，其他项目使用上述版本。

## 常用命令

运行测试：

    ./mvnw clean test

启动服务：

    ./mvnw spring-boot:run

## 多门课程原子调课

一次调课以「调课方案」为单位，方案内可包含多条现有课程安排的调整，每条调整指定新的星期/时段（`newTimeSlot`，格式同课程时间段，如 `周三 10:00-12:00`）和新教室（`newClassroom`）。

### 主要业务规则

1. **方案组成**：一个方案至少包含一条调整，且引用的课程安排 ID 互不重复；提交时会保存每条课程的原始排课内容（课程名、老师、教室、时间段）作为快照。
2. **预检查**：检查冲突时把方案内课程即将腾出的旧时段/旧教室视为可用，因此允许两门或多门课程互换时段；但调整后的新时段/新教室不得与未参与调课的课程产生教师或教室冲突，方案内部的新安排之间也不得冲突。任一调整不合法都会返回整份方案的全部冲突明细（`canReschedule=false`）。
3. **原子确认**：确认时在写锁内重新校验——每条课程仍存在、且与提交时的快照一致（未被别人修改/删除）、目标资源未被占用、方案内部无冲突。全部通过才一次性应用所有变更；任一失败则整份方案不生效，不留部分调课结果。多个方案并发修改同一课程时最多一个成功（其余因快照不一致而失败，方案保持待处理）。
4. **幂等**：提交必须携带调课业务号 `bizKey`。相同业务号且方案内容相同重复提交时返回首次提交的结果（HTTP 200）；内容不同则返回 409 冲突。方案确认（CONFIRMED）或拒绝（REJECTED）后不可再次预检/确认/拒绝。
5. **审计**：确认成功后为每条课程写入一条 `RESCHEDULE` 审计日志，同时记录调整前（`previousClassroom`/`previousTimeSlot`）与调整后（`classroom`/`timeSlot`）的内容。

### 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/reschedule-plans` | 提交调课方案（按 `bizKey` 幂等；新建 201，重复提交 200） |
| GET | `/api/reschedule-plans` | 查询全部调课方案 |
| GET | `/api/reschedule-plans/{id}` | 查询方案详情（调整明细、冲突明细、处理结果） |
| POST | `/api/reschedule-plans/{id}/pre-check` | 预检查，返回整份方案的冲突明细 |
| POST | `/api/reschedule-plans/{id}/confirm` | 原子确认；存在冲突时返回 409 及冲突明细，方案不生效 |
| POST | `/api/reschedule-plans/{id}/reject` | 拒绝方案 |

提交示例：

```json
POST /api/reschedule-plans
{
  "bizKey": "RES-20260927-001",
  "items": [
    {"scheduleId": 1, "newClassroom": "B202", "newTimeSlot": "周二 14:00-16:00"},
    {"scheduleId": 2, "newClassroom": "A101", "newTimeSlot": "周一 08:00-10:00"}
  ]
}
```

## 教室临时停用与成组修复排课

教室因检修、活动等原因临时停用时，先登记「停用事件」，系统把所有受影响课程**冻结为一份修复任务**，再由一份「修复方案」把全部受影响课程成组重新安排。

### 停用事件与修复任务

1. **停用生效**：停用事件指定教室、一个或多个停用时间段（格式同课程时间段）、原因和外部事件号 `eventNo`。生效时立即扫描全部课程安排，凡「教室相同且时间段重叠」的课程都被冻结进同一修复任务，保存冻结时的排课内容与课程版本快照；无冲突课程时不产生修复任务。
2. **幂等与冲突**：相同 `eventNo` 且教室/原因/时间段完全相同的重复提交返回首次结果（HTTP 200）；同号异内容返回 409。冻结内容以首次生效时为准，重复提交不会重新扫描。
3. **停用即约束**：停用生效后，新增、修改、批量改时段、普通调课、修复确认都不允许把课程安排进该教室的停用时段（预检查与确认时均会校验，冲突类型 `OUTAGE_BLOCKED`）。
4. **范围调整**：`PUT /api/room-outages/{id}` 可调整停用时间段或原因，可携带 `expectedVersion` 做乐观并发控制，每次调整版本递增并保留范围变更历史。范围扩大后新冲突的课程（含已修复后又落入新范围的课程）会追加进或重新打开同一修复任务；范围缩小后已不在停用窗内的冻结课程标记为自然消解。
5. **停用取消**：取消后教室时段恢复可排，但**不会自动回退已经完成的修复**；尚未修复的课程保持原状，修复任务关闭（CANCELLED）。如需恢复原排课，应按普通调课流程创建一份**新的调课方案**，停用事件、修复前后的安排与处理人员记录均完整保留。

### 修复方案

1. **全覆盖**：修复方案必须、且只能覆盖修复任务中当前全部待修复课程；可以换教室、换时段，也可以在多门课程之间交换资源（规则与普通调课一致：方案内腾出的旧时段/旧教室视为可用）。缺门（`missingScheduleIds`）或引用任务外课程（`extraScheduleIds`）时不允许提交，更不能确认部分方案。
2. **预检查**：沿用教师冲突、教室冲突、方案内部冲突规则，并检查目标教室是否处于停用范围；对每一门无法安排的课程给出具体原因（冲突类型包括 `TEACHER`/`CLASSROOM`/`INTERNAL_*`/`OUTAGE_BLOCKED`/`NOT_COVERED`/`VERSION_CONFLICT`/`SCHEDULE_CHANGED`/`SCHEDULE_NOT_FOUND`）。
3. **原子确认**：确认时在共享写锁内重新检查课程版本、教师时间和目标教室当前停用状态，全部通过才在一次事务中应用所有变更；任一失败整份方案不生效，方案保持待处理并返回全部冲突明细。成功后修复任务完成，每门课程写入 `REPAIR_CONFIRM` 审计日志（修复前后教室/时段、处理人员 `operator`、修复业务号 `bizKey`）。
4. **幂等与状态**：修复方案按 `bizKey` 幂等（同号同内容返回首次结果，同号异内容 409）；确认或拒绝后不可再次处理。

### 并发控制

课程安排带有单调递增的 `version`（每次排课内容被修改即递增），普通调课与修复方案提交时都会快照课程版本。普通调课确认、停用范围调整、修复确认共用同一把读写锁串行执行：旧方案确认时若课程版本已变化（存在较新的调课/修复/修改）则按 `VERSION_CONFLICT` 失败，不会覆盖较新安排；若停用范围被调整过，移入新停用范围的方案按 `OUTAGE_BLOCKED` 失败。

### 停用修复与普通调课的关系

- 二者使用同一套原子调整引擎（版本快照、腾出资源视为可用、教师/教室/停用范围冲突校验、一次事务应用），区别只在于**来源和覆盖要求**：普通调课是人工选择任意课程发起，覆盖提交的调整即可；停用修复由停用事件冻结的修复任务驱动，必须覆盖任务中全部待修复课程。
- 停用取消后不自动恢复原排课；恢复原排课走普通调课（新建调课方案），从而在变更链上保留「停用 → 修复 → 再调课」的完整轨迹。
- 普通调课同样受停用范围约束，无法借调课把课程排入停用时段。

### 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/room-outages` | 停用生效并冻结修复任务（按 `eventNo` 幂等；新建 201，重复 200） |
| GET | `/api/room-outages` | 查询全部停用事件 |
| GET | `/api/room-outages/{id}` | 查询停用事件详情（含范围变更历史、关联修复任务） |
| PUT | `/api/room-outages/{id}` | 调整停用范围/原因（可带 `expectedVersion`） |
| POST | `/api/room-outages/{id}/cancel` | 取消停用（已完成的修复不回退） |
| GET | `/api/room-outages/repair-tasks` | 查询全部修复任务 |
| GET | `/api/room-outages/repair-tasks/{taskId}` | 查询停用影响范围：冻结的受影响课程与修复状态 |
| POST | `/api/repair-plans` | 提交修复方案（按 `bizKey` 幂等；新建 201，重复 200） |
| GET | `/api/repair-plans` | 查询全部修复方案 |
| GET | `/api/repair-plans/{id}` | 查询修复方案（调整明细、冲突明细、覆盖情况、处理人员） |
| POST | `/api/repair-plans/{id}/pre-check` | 预检查，逐门给出无法安排的具体原因 |
| POST | `/api/repair-plans/{id}/confirm` | 原子确认（请求体可带 `operator`） |
| POST | `/api/repair-plans/{id}/reject` | 拒绝修复方案 |
| GET | `/api/schedules/{id}/change-chain` | 查询课程变更链（创建、调课、停用冻结、修复确认等） |

停用生效示例：

```json
POST /api/room-outages
{
  "eventNo": "OUTAGE-20260928-001",
  "classroom": "A101",
  "reason": "投影仪检修",
  "timeSlots": ["周三 10:00-12:00"],
  "operator": "教学楼管理员"
}
```

修复方案提交示例：

```json
POST /api/repair-plans
{
  "bizKey": "FIX-20260928-001",
  "taskId": 1,
  "operator": "教务处",
  "items": [
    {"scheduleId": 3, "newClassroom": "B202", "newTimeSlot": "周四 08:00-10:00"}
  ]
}
```
